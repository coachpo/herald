# Herald 多目标广播与条件路由最小实施计划

修订：1。日期：2026-11-09。状态：实施基线，功能尚未实现。

## 目标与边界

复用现有一消息多 delivery 的广播能力，只增加接收阶段的条件选目标。消息、最终选中的全部投递任务及路由说明必须原子提交；后续发送与重试不重新匹配规则。

保持单用户、一个常驻 FastAPI 进程、SQLite 和现有有界 worker。保留接收幂等、独立重试、成功历史、未完成工作保留及既有凭据和出站安全约束。已持久化的 `sent` 不再发送；外部接受后、成功记账前崩溃仍可能重复，投递保证仍为至少一次。

不增加独立广播端点、消息中间件、通用规则引擎、新依赖、路由预览接口或规则历史服务。不增加 `source/category/tags`，不做配置快照、主备切换、负载均衡和冗余链路。

## 已确定的行为

| 项目 | 本次实现约定 |
| --- | --- |
| 显式目标 | 非空 `target_ids` 只投指定目标，绕过规则和默认目标；重复 ID 去重；`[]` 拒绝 |
| 自动选择 | 省略或 `null` 时匹配规则；零条命中才回退全部启用的默认目标 |
| 匹配字段 | `priority` 支持 `eq/gte/lte`，值为严格的 1–5 整数；`title/body` 支持 `eq/prefix/contains`，按原文区分大小写，不自动裁剪或改写 |
| 规则组合 | 每条规则的非空 `all` 条件全部满足才命中；数组从上到下扫描，跳过禁用规则；全部命中目标取并集，不停止、不覆盖 |
| 顺序 | 数组顺序用于配置与命中说明；不决定目标优先级或实际发送顺序 |
| 失效目标 | 所选目标必须全部存在且启用，否则整体拒绝；不静默跳过、不部分接收、不改投默认目标 |
| 无目标 | 返回 `400 no_targets`，不写入消息或任务，不提供接受后静默丢弃模式 |
| 规则引用 | 保存时校验所有规则引用的目标存在，接收时校验所选目标启用；删除目标前必须解除所有规则引用，包括禁用规则 |
| 配置变化 | 规则和默认集合只影响新接收；禁用目标不取消既有任务；领取任务仍读取目标最新配置 |
| 幂等 | 先检查已有 key，再选择目标；请求指纹算法不变，不加入规则版本或计算出的目标集合 |

无规则时与现有行为一致。启用规则后，已有省略 `target_ids` 的客户端会对新请求采用规则路由，这是本次接受的行为变化。显式指定目标仍可绕过规则，因此规则不承担不可绕过的强制归档职责。

## P1 契约与匹配器

责任角色：后端实现者。先完成以下契约与纯匹配逻辑，供后端集成和前端使用；不假设需要额外人员。

### API

| 接口 | 变更 |
| --- | --- |
| `GET /api/routing` | 管理令牌鉴权；返回 `{revision, rules}`，初始为 `{revision: 0, rules: []}` |
| `PUT /api/routing` | 管理令牌、JSON；提交读取时的 `revision` 和完整规则数组；原子替换，成功返回递增后的版本及规范化规则，状态码 `200` |
| `POST /api/ingest`、`POST /api/messages` | 请求结构、鉴权和回执结构不变，共用接收事务；首次接收 `201`，同请求重放 `200`，冲突 `409` |
| 消息列表与详情 | 增加可空 `routing_decision`；不改变分页、delivery 字段和手动重试接口 |
| `DELETE /api/targets/{id}` | 保留未完成任务检查；新增规则引用检查，引用未解除时返回 `409 target_referenced_by_routing` |

规则示例，目标 ID 为占位值：

```json
{
  "revision": 0,
  "rules": [
    {
      "id": "urgent",
      "enabled": true,
      "all": [{"field": "priority", "op": "gte", "value": 4}],
      "target_ids": ["target-id"]
    }
  ]
}
```

`id` 为配置内唯一的非空稳定字符串；`enabled` 默认 `true`；条件与目标列表均不能为空；目标列表排序、去重。类型、字段、操作符必须匹配，未知字段及非法表达式返回 `422`。引用不存在的目标返回 `400 target_unavailable`。版本不匹配返回 `409 routing_changed`，不更新配置；空规则数组是合法的清空操作，仍递增版本。

`routing_decision` 结构固定为：

```json
{
  "mode": "rules",
  "rules_revision": 1,
  "matched_rule_ids": ["urgent"]
}
```

`mode` 取 `explicit/rules/defaults`。显式选择时版本为 `null`、命中列表为空；自动选择记录读取的版本，默认回退时命中列表为空。旧消息整个字段为 `null`。只保存版本和规则 ID，不复制完整规则、消息正文或目标配置；此说明不是完整历史规则审计，也不用于重新计算目标。

### 实现落点与验收

- 在 [models.py](../../backend/models.py) 增加有类型的规则与配置输入，保留 `MessageInput` 不变。
- 新增 `backend/routing.py`，只承担纯匹配及命中集合计算；不访问网络或数据库，不解释脚本、正则或嵌套表达式。
- 输入按现有消息默认值规范化后匹配；输出命中规则 ID 和去重目标 ID，不能仅以输出目标为空代替“零规则命中”。
- 验收：操作符、边界值、AND、多规则合并、禁用规则及顺序不影响最终集合均有确定性测试；接口与错误约定可供 P2、P3 直接使用。

## P2 数据库迁移与接收集成

责任角色：后端实现者。依赖 P1 的模型和匹配结果契约。

### Schema v1 升级到 v2

在 [database.py](../../backend/database.py) 增加明确的增量迁移，不引入迁移框架：

1. 新建单例表 `routing_config`：固定主键、非空 `revision`、非空 `rules_json`；初始版本 `0`、规则 `[]`。
2. `messages` 增加可空 TEXT 列 `routing_decision_json`；旧消息保持 `NULL`。
3. 空库直接初始化 v2；v1 在一个事务内迁移；v2 重复初始化不重置规则或版本；不支持的更高版本继续拒绝启动。
4. DDL、初始数据和 `PRAGMA user_version=2` 一起成功或回滚。保留原消息 ID、幂等 key/指纹、全部 delivery 状态及计数、加密配置、外键和唯一约束。
5. 将 [Store.receive](../../backend/store.py) 中不带列名的消息 INSERT 改为显式列名，读接口解析 JSON 为 `routing_decision`，不暴露内部原始 JSON 列。

迁移仍在取得现有独占进程锁后执行，保留 WAL、`synchronous=FULL`、外键及短事务。升级前沿用既有备份流程；不提供降级迁移，也不承诺旧程序可直接读取 v2。

### Store 与 API

- 增加规则配置读取、更新操作，在同一写事务内校验版本、目标引用、替换内容并递增版本；注册 P1 的两个管理接口，沿用现有 JSON、鉴权和安全错误处理。
- 接收流程保持：校验及原指纹 → 写事务 → 已有 key 重放或冲突 → 显式目标或读取规则并匹配、必要时默认回退 → 校验全部目标 → 写消息、决策、全部 pending deliveries → 提交 → 回执。
- 不在 HTTP 层提前固定路由结果，不缓存一份可能过期的配置参与接收；配置更新与接收通过现有 SQLite 写事务串行化，每次接收使用完整的一个配置版本。
- 删除目标时，在同一事务内完成未完成任务及规则引用检查。规则保存在 JSON 中，引用检查由 Store 负责，不另建规则目标关联表。
- 自动重试、手动重试、重启恢复均只使用已持久化的 delivery，不重新匹配规则，不新增目标，不触碰其他 `sent` 任务。
- [worker.py](../../backend/worker.py)、provider、发送超时和退避机制无需改造；仍在领取事务提交后发送，保留领取时读取目标最新配置的语义。

验收：接收成功后可从另一连接读到完整消息、决策及所有任务；失败没有部分写入。规则变更和目标状态变化不改变已有幂等回执或既有任务集合。

## P3 前端最小调整

责任角色：前端实现者，可以与后端为同一人。P1 契约固定后可开始，联调依赖 P2。

- 在现有 [Targets.tsx](../../frontend/src/Targets.tsx) 下加入规则管理区，不新增顶层导航、客户端路由或可视化流程编辑器。规则编辑拆为独立组件和必要的 hook，避免继续混合目标凭据表单与规则职责。
- 提供规则增删、启停、条件增删、字段及操作符选择、值输入和目标多选；整份保存，保留稳定规则 ID 与数组顺序，不做拖拽排序。
- 新增相应 DTO，沿用 [api.ts](../../frontend/src/lib/api.ts) 的管理令牌和错误处理。保存成功采用服务端返回的新版本；版本冲突提示重新加载，不自动覆盖，也不静默丢弃未保存编辑。
- 调整 [useComposer.ts](../../frontend/src/hooks/useComposer.ts) 和 [SendMessage.tsx](../../frontend/src/SendMessage.tsx)：自动模式改为“按规则选择，无命中使用默认目标”；只有显式模式才要求本地至少选择一个目标。自动模式即使没有默认目标也可提交，由服务端判断是否可接收。
- 自动模式不把默认目标列表或数量当作最终投递集合；不在浏览器复制规则匹配器。显式模式继续提交非空 `target_ids`，自动模式继续省略该字段。
- 在 [MessageDetail.tsx](../../frontend/src/components/MessageDetail.tsx) 展示选择方式、版本、命中规则 ID；旧消息显示未记录路由说明，不猜测原选择方式。最终目标和状态仍以 deliveries 展示。
- 同步 [Connection.tsx](../../frontend/src/Connection.tsx)、目标页与 [TargetForm.tsx](../../frontend/src/components/TargetForm.tsx) 的默认目标说明：仅在自动路由零命中时回退。删除被引用目标时给出解除规则引用的提示。
- 保持凭据存储、文本渲染、回执不等于投递成功、仅失败任务可手动重试的现有行为。不引入 `as any` 或 TypeScript 忽略指令。

验收：用户可在现有工作区完成规则配置、自动发送、显式广播和查看路由结果；没有默认目标但规则可命中时，前端不拦截发送。

## P4 回归验证与文档

责任角色：集成负责人，汇总后端、前端结果并完成最终验收；可以由同一实施者承担。新增测试随 P1–P3 落地，不留到最后才编写。

### 自动化回归范围

| 层次 | 必须验证的行为 |
| --- | --- |
| 纯匹配器 | 各字段及操作符、整数类型和 1/5 边界、字符串大小写和原文语义、规则内 AND、全部命中合并去重、禁用规则、顺序不改变目标集合 |
| 配置 API | 管理与 ingest 令牌隔离、JSON 要求、非法字段/操作符/值及重复规则 ID、缺失目标引用、初始空配置、清空规则、版本递增和冲突不写入 |
| 接收 API | 两个端点语义一致；显式选择绕过规则；省略和 `null` 自动选择；`[]` 拒绝；命中后不附加默认；无命中回退；无目标或任一所选目标不可用时无部分接收 |
| 幂等与原子性 | 原指纹兼容；目标顺序及重复 ID 等价；规则修改后同键重放不重算、不新增任务；跨端点重放及不同请求冲突；扇出中途失败回滚消息、决策与全部任务 |
| 并发与引用 | 并发配置更新只有正确版本可成功；配置更新与接收使用完整的旧版本或新版本；目标删除与规则更新不留下悬空引用，包括禁用规则引用。用屏障或事件协调，不靠睡眠猜测时序 |
| 迁移 | 用临时 v1 数据库覆盖 pending/sending/retry/sent/failed、幂等记录及加密配置；升级后查询、重放、恢复和重试仍工作；旧说明为空；新库与重复初始化正常；模拟迁移中途失败后 schema 和版本不部分更新 |
| worker 与历史 | 增加一条规则扇出用例：A 成功、B 失败，重试仅影响 B，保留总尝试次数；复用既有 lease、崩溃恢复、有界并发、清理保留和目标删除历史回归；验证禁用目标不取消已接收任务、后续领取使用最新同类配置 |

纯匹配与迁移分别放入 `backend/tests/test_routing.py`、`backend/tests/test_database.py`；接收及配置的可观察行为优先扩展现有 [test_store.py](../../backend/tests/test_store.py)、[test_api.py](../../backend/tests/test_api.py)、[test_worker.py](../../backend/tests/test_worker.py)。所有数据库使用临时目录，provider 使用 mock，不发送真实通知。不增加仅检查源码文本或符号存在的测试。

### 浏览器回归

当前没有前端测试运行器；不为本次功能引入一套新框架。使用临时数据目录和受控 mock 投递验证：

1. 配置高优先级规则与另一条重叠规则，保存、刷新后仍可读取；另一个页面用旧版本保存时提示冲突且不覆盖。
2. 规则有可用目标、默认目标为空时，自动发送可提交，详情展示正确规则版本、命中 ID 和去重目标；零命中且无默认时展示服务端错误，不产生成功回执。
3. 无命中有默认时回退；显式选择两个目标时绕过规则；显式空选择仍被拦截。
4. 规则修改不改变旧消息的决策说明或任务；旧消息正常展示；成功任务无重发按钮，失败任务可独立重试。
5. 被规则引用的目标删除失败并给出可操作提示；键盘可操作规则表单，窄屏无阻塞编辑的溢出，401 沿用现有退出处理。
