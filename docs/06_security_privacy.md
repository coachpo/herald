# Security and privacy

One owner controls the instance using a high-entropy management bearer token. Senders receive a different ingest token with permission only to submit messages. Herald has no account signup, password, session refresh, or tenant model. Bearer tokens are SHA-256 hashed before constant-time comparison; transport still requires TLS when leaving the local host.

At first start, Herald creates `credentials.env` with mode 600 in its private data directory (mode 700). Existing directories with group/other access are rejected; the application does not change their permissions silently. It contains the admin token, ingest token, and Fernet encryption key. Preserve this file, never commit it, and retrieve tokens through a private operator session. Alternatively supply all three credential environment variables together. Changing the encryption key does not re-encrypt existing target rows and makes them unreadable.

Target configurations are encrypted in SQLite and redacted in management responses. Message bodies, target names, delivery state, and other history are not encrypted by the application. Restrict filesystem and backup access; use host storage encryption if required. Logs and errors must not contain raw tokens, target credentials, decrypted configs, payload bodies, or credential-bearing URLs.

The browser keeps its management token in session storage, clears it on logout, and renders messages as text. It must not persist tokens in localStorage or inject message content as HTML. Use the API's same-origin built dashboard or the supported Vite proxy; no permissive CORS bypass is required.

Provider destinations are checked for SSRF at target creation and before each send. The check resolves all returned addresses and rejects loopback/private/link-local destinations. HTTP clients retain TLS hostname/certificate verification and do not follow redirects; MQTT destinations receive the same address checks. DNS validation and the actual client connection are separate operations, so connections are not pinned to the checked addresses. Administrators must use trusted provider hostnames and configure any required proxy destination restrictions operationally. Do not disable these checks to make tests pass or reach private providers.

The API defaults to loopback; container publishing is loopback-only. Put remote access behind a TLS reverse proxy and a deliberate firewall rule. Only one process may own a data directory. No exactly-once external delivery is claimed: a crash can cause provider duplicates. Pending and failed records are not automatically deleted; successful history uses the configured retention threshold.
